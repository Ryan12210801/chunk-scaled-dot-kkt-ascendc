## 一、项目结论与总时间线

### 1.1 一句话概括项目

这个项目不是简单地把一个矩阵乘法写得更快，而是围绕一个固定 64-token chunk 的算子，把**数学语义、分组头复用、Cube/Vector 分工、片上与片外数据布局、流水依赖、固定形状代码生成，以及目标工作负载上的实测结果**统一起来。[S01–S03][C01–C03]

优化过程的中心逐渐变化：最初是“算得对”；随后是“不要重复算同一个 Gram”；再往后是“不要让 AIC 和 AIV 相互等待”；最后则是“不要因为过早搬运、过度预取或不合适的调度，把局部节省抵消掉”。后两点是代码与实验现象支持的工程认识，不应扩展成所有 Ascend 算子的固定规律。[C01][H03–H06]

### 1.2 最重要的已确认结论

**正确性方面：**主参考是题面 3.1 的 Python 公式，其条件为 `g_i - g_j < 0`。不能额外叠加位置下三角，也不能直接用位置下三角替代。tail 的逻辑宽度、Matmul 的实际输出行距和 AIV 的 64 列工作布局必须分清。局部单调数据和单任务测试会遮蔽这些错误。[S01][S02]

**架构方面：**按 `(chunk, kvHead)` 计算一次 KKT，再供对应的 R 个 query head 使用，是主线最明确的复用结构。AIC 负责 Gram，两个 AIV 负责缩放和输出；通过每组两个 GM workspace slot 与 READY/FREE 协议形成任务流水。FREE 对应“GM 中的 KKT 已读完”，不是“整个后处理完成”。[C01–C03]

**向量方面：**BRCB、repeat-stride、double-head 的价值在于减少逐行标量控制、组织好广播和小块搬运，并增加可调度的独立工作，不是把数学上独立的两个头混在一起。删除 barrier 只有在依赖和存储生命周期仍成立时才是优化。[C01][H01][W02]

**手写 Cube 方面：**固定 `64×64×128/256` 的结构确实有机会减少通用 Matmul 的调度负担，但初版低阶化并不自动更快或更稳定。项目里最耗时的故障集中在 L0A/L0B 复用与跨 task 事件生命周期。先通过 fail-closed 的 Host 路由只开启已验证路径，才使迭代能够继续。[S03–S05]

**后期性能方面：**更多 overlap、更多 buffer、MTE3 越早发射，都不是无条件成立的优化准则。Phase C 的较晚输出发射优于较早发射；KKT double-buffer/next-task prefetch 略有退化；部分局部 trace 收益并没有转化成 Judge 收益。[H03][H05][S08–S10]

**最终状态方面：**能够确认多代有效基线，但还不能把当前挂载的旧文件宣布为整个项目最后一次提交的唯一最优版本。八月下旬的调度分支已有用户反馈，但最后采用的阈值、完整代码包和逐 case 结果没有在本轮全部恢复。[S06][C01][H06]

## 二、拿到题目后的分析与实现思路

### 2.1 首先确定算子的真实计算对象

题面输入为：`k` 的形状 `[B,T,Hg,K]`、BF16；`beta` 为 `[B,H,T]`、BF16；`g_cumsum` 为 `[B,H,T]`、FP32；`chunk_offsets` 为 INT32 边界数组。输出是 FP32 `[B,H,T,64]`。当前题目固定 `B=1`、chunk size 为 64，`K∈{128,256}`，且 `Hg` 整除 `H`。[S01]

令 `R=H/Hg`。一个 query head `h` 对应的 KV head 为 `floor(h/R)`。对区间 `[s,e)`，令 `L=e-s≤64`，则在有效列内：

```text
G[i,j] = sum_d K[s+i, kvHead, d] * K[s+j, kvHead, d]

A[h,s+i,j] = beta[h,s+i] * exp(g[h,s+i]-g[h,s+j]) * G[i,j]
             当 g[h,s+i]-g[h,s+j] < 0 时

其余位置为 0；特别是 j >= L 的输出 padding 列为 0。
```

这里没有额外的 `1/sqrt(K)`，也没有要求把 beta 乘在列 `j` 上。`scaled` 这个名称本身不能代替公式。主参考中也没有额外的负号或位置条件 `j<i`。[S01]

题面给出的规模范围是：1–4 条序列，每条长度 `[1k,64K]`，拼接后 T 为 `[1k,256k]`；H 为 1–128，Hg 为 1–32。这里保留原文的 k/K 记法，不擅自解释为十进制还是二进制。题面精度写为相对误差不超过 `1e-5` 或绝对误差不超过 `1e-6`。[S01]

### 2.2 把“必需计算”和“可复用计算”分开

同一个 chunk、同一个 KV head 的 Gram 只取决于 K，与 beta、g 或被重复映射到它的 query head 无关。因此天然任务不是 `(chunk, queryHead)` 的完整重算，而是先按 `(chunk, kvHead)` 计算，再处理 R 份 head-specific epilogue。[S01][C01]

本轮推导：如果逐 query head 重算 Gram，那么这部分矩阵乘法工作量可能比共享实现多 R 倍。减少的是 **Gram 部分**，不是整个算子的总耗时；R 份后处理和 R 份输出仍然存在。这是报告中必须限定的收益口径。

完整 chunk 的单个 Gram 约为 `2×64×64×K` 次浮点运算，而每个 head 还要生成 4096 个输出。R 越大，AIC 计算的摊销越充分，AIV 和输出路径的重要性通常越高。这是工作量分析给出的方向，不是对每个 shape 的瓶颈判决。

### 2.3 自然的硬件映射

主线把 BF16 矩阵乘法放到 AIC/Cube，把比较、指数、beta 缩放、mask 和输出放到 AIV/Vector。中间结果以 FP32 KKT 进入 workspace，随后被 AIV 消费。项目后期采用 MIX 1:2，也就是一个 AIC 配对两个 AIV 的工作组织。[C01–C03][S07]

最初应该优先让这种分工的数学与数据流正确，而不是同时引入手写 MMAD、复杂 task 重排和大量 tiling key。实际过程也证明，多层变化一起上时，数值错误、布局错误和同步错误很难区分。[S02–S05]

### 2.4 变长约束如何影响设计

边界来自 `chunk_offsets`，不能仅用 `chunkId×64` 推导 chunk 起点。多条序列拼接后，前一条的 tail 后面可能立刻开始另一条序列的完整 chunk。题面例子 `[0,64,100,164,228,240,300]` 就包含这种情况。[S01]

在每条序列按 64 切分的约束下，每条序列最多一个 tail，因而 1–4 条序列对应最多 4 个 tail。这给了 full64 热路径优先优化的依据，但不能据此省略 tail 正确性。用于排障的 L=1、2、37 等微型输入可以超出题面性能用例的序列长度范围；它们是边界验证，不代表实际评分权重。[S01][H02]

### 2.5 第一版实现的合理目标

第一版的可验收目标可以整理为：独立 CPU golden；GM 直接输入高阶 Matmul；确认 K 的真实行距；明确 full 与 tail 输出布局；AIV 完成严格的主参考 mask；最后覆盖多个 chunk、多个 head 和多个核。这里的“合理目标”是结合当时经历重建的工作顺序，不冒充第一天已经完整写出的设计文档。[S02][S13]

## 三、初版功能正确的过程

### 3.1 编译通过只是第一道门

早期日志包含最基础的工程问题：源码出现多余 `!` 导致 `expected unqualified-id`，使用当前 CANN 环境没有的接口导致编译失败，以及旧新入口与类签名不匹配。7 月 20 日已有“Build completed successfully”的日志，但它只证明这一轮工程构建成功，不能等同算子输出全部正确。[S15]

后续还出现 `SetSubBlockIdx` 不存在的报错；八月的一轮编译则同时出现 K128 类名不匹配、`Init` 多传 beta、把非模板 VectorStage 当模板实例化等问题。这些不是数值算法问题，而是 API 版本和文件契约问题。错误日志中的 `SetSysWorkspace` deprecated warning 也不能替代真正的 error 定位。[S15]

### 3.2 最关键的语义陷阱：三套参考并不一致

早期复盘明确指出：文字描述强调 strictLower；Triton 示例包含 safe_exp 和三角约束；Python 3.1 主参考仅按 `diff<0` 筛选。题面又明确指定以 3.1 为主。[S01][S02]

当时先采用 `diff<0 AND j<i`，Judge 反馈约 23% 错；之后错误地只保留 `j<i`，反馈接近 50%。这两轮说明“把多个看似合理条件叠起来”不是忠实实现。最终应当跟随唯一主参考，而不是把题名、背景知识和示例代码中的条件做并集。[S02]

必须保留的口径说明：这些比例来自历史记录。旧复盘把它们解释为 mask 不一致的诊断信号，但不能据此严格推断 hidden input 的随机分布，更不能把 Judge 的反馈比例自动当成逐元素错误比例。后续项目已明确要求把 Judge UI 的 Wrong ratio 与完整样本通过情况区分开。[S02][H07]

### 3.3 为什么本地测试没有及时发现

本地测试使用单调递减的 g。在这种构造下，`g_i<g_j` 与 `i>j` 相一致，于是错误的三角 mask 在测试中看起来正确。问题不是“测试次数不够”，而是数据没有区分竞争语义。[S02]

本轮给出一个最小反例：`g=[0.1,-0.3,0.4]`。位置 `(i=0,j=2)` 满足 `g_0<g_2`，虽然它位于位置上三角；若 K 的点积和 beta 非零，该输出就应该非零。因此，跳过 row 0 或只算下三角都会遗漏主参考允许的结果。相等 g 则应因严格 `<0` 而被屏蔽。[S01；本轮推导]

### 3.4 输入的逻辑矩阵不是物理连续矩阵

固定 KV head 后，逻辑输入看起来是 `[L,K]`，但原 K 存储为 `[T,Hg,K]`。相邻 token 同一 KV head 的起点相差 `Hg×K` 个元素，而不是 K。矩阵乘法的逻辑 K 维与原始 GM 行距必须分别传递。[S02][C01]

当前挂载的高阶基线中，`SetOrgShape` 的原始 A/B 行距参数使用 `hg*K_DIM`，`SetSingleShape` 才使用当前 chunk 的 L 和 K_DIM。报告中可以用这个细节说明：算子“形状正确”并不等于访存“步长正确”。[C01，约 147–170 行]

### 3.5 剩余小比例错误：compact tail 与 64 列工作布局

语义修正后，历史记录仍有约 0.7%–1.3% 的残余错误。通过实际输出布局观察，发现 tail 的高阶 Matmul 结果是 compact `[L,L]`，而不是此前假设的 `[L,64]`。例如 L=37 时，相邻行起点相差 37 个 FP32 元素。[S02]

这里有三层宽度：有效列数 L、Matmul 在 GM 的物理行距、AIV 对齐工作区的行距 64。将其中两层混同，就会从错误位置读取下一行，或把前后行的数据带进 padding 列。

当时的修复方向是把 compact 行显式转换到 64 列对齐 UB：先清零目标行，再只 Gather L 个有效元素，Gather 偏移以字节计数。不能无条件 Gather 64 个值，因为它会跨越 compact 行边界，甚至越过有效数据末端。[S02]

### 3.6 Padding 不是“搬运后自然正确”

`DataCopyPad` 的对齐填充不能被理解为“一定填满业务需要的 64 列”。AIV 的完整输出行可能包含有效列之外的旧值。即使某个 g mask 恰好屏蔽这些值，也不能靠这种偶然性保证正确。[S02]

因此 tail 必须有明确的有效列约束 `j<L`，并保证 `[L,64)` 最终写零。把输出预先填成 `12345.0` 之类 poison 值，是检测遗漏写回的有效诊断；poison 不是最终计算的一部分。[S02]

### 3.7 为什么“只改 tail”有时连 full 都挂

早期记录中，tail 标量 `GetValue/SetValue` 搬运方案曾在 L=37 卡住；新增 tail buffer 后，未直接修改的 full64 基本用例也发生挂起；再通过复用 buffer 调整后，tail 通过但多头、多任务仍不稳定。[S02]

原复盘将其与 UB 分配、内联后的代码结构、别名和生命周期相互影响联系起来。这是该次排障的解释，不应写成“GetValue API 本身必然死锁”或“任何多开一个 buffer 都会改变结果”。真正可迁移的措施是隔离 full 与 tail 代码，冻结已验证的 full 热路径，让 tail 的 Gather、临时区和特殊处理不侵入 full 的资源规划。[S02]

### 3.8 形成可靠功能基线的验收矩阵

历史复盘要求覆盖 L=1、2、31、37、63、64，K=128/256，R=1 与分组复用，多个 chunk、多条序列，以及非单调、相等、接近零差值的 g；beta 也应覆盖不同符号。测试还要从单 task 扩展到多 task 和多轮 kernel 调用。[S02]

错误应分别检查：有效输出区、padding、row 0、跨 head/跨 chunk 污染，以及 NaN/Inf。调试输出全部移除后，还要重新跑一次 correctness，避免把带 DumpTensor 的诊断程序当成提交版本。源文件、构建产物、安装的自定义 OPP 和测试二进制也必须同步更新。[S02]

**本阶段最终经验：**先证明实现的是同一个算子，再证明读写的是同一块数据，最后证明在多个任务下仍然正确。某一个“简单样例全对”不足以跨过这三道门。

## 四、AIC/AIV 分工与任务级流水

### 4.1 从两阶段到持续生产—消费

恢复到的 7 月 25 日源码采用 two-stage MIX 思路：AIC 对所有 `(chunk,kvHead)` 计算 KKT，按全部 task 预留 workspace，再交给 Vector 阶段。后来现存 V6.7.1 基线则是每组只保留两个 workspace slot，通过局部 READY/FREE 协议持续生产和消费。[S13][C01]

这是两个不同层次的变化：复用减少重复 Gram；流水则降低阶段之间的等待，并将中间存储从“按全部任务规模分配”改成“按核组数与 slot 数分配”。不能把二者揉成一句笼统的“融合提速”。

### 4.2 任务切分与两个 AIV 的分工

当前高阶基线中，task 编号为 `chunkId*Hg+kvHeadId`，每组按 `groupId + round*blockDim` 循环取任务。Host 使用 `blockDim=min(AIC核数,NT*Hg)`，保证每个选中的 AIC 组有任务。[C01][C03]

R≥2 时，两个 AIV 保持完整行，各自处理 query head 重复区间的一半。区间是按整数比例划分的连续范围，不是所有版本都采用同一个“奇偶 head”策略。R=1 时没有足够的 head 可切，退回两个 AIV 各处理最多 32 行。[C01]

例如 R=4，两个 AIV 各负责两个 head；R=3，则一侧一个、另一侧两个，天然存在负载不均。后期 R=3 相关实验正是围绕这一问题，但具体方案需要分别记录，不能因为提过“均衡”就宣称已经解决。[C01][H02][S09]

### 4.3 Workspace 双 slot 的基本协议

每个 Gram tile 是 `64×64×4=16384` 字节。两个 slot 对应每组 32 KiB 的用户 workspace。高阶基线使用 READY 7/8、FREE 9/10 两组交替 flag；具体数字属于这份实现，不是通用模板必须使用的编号。[C01]

```text
AIC，round r：
  slot = r % 2
  若重用旧 slot：等待两个 AIV 的 FREE
  生产 KKT 并通过 Fixpipe 写到 GM
  在 PIPE_FIX 顺序之后发布 READY

每个 AIV，round r：
  消费本轮 READY
  把自己需要的 KKT 从 GM 搬到 UB
  KKT 读取完成后发布 FREE（仅当未来会重用）
  用本地 KKT 完成后处理与输出
```

官方模式 2 的同步说明与这种成组关系一致：AIC 一侧通知配对的两个 AIV；反向需要两个 AIV 都通知后，AIC 才继续。本轮仅借官方资料核对通信语义，不把其他版本文档中的所有限制直接套到当前 CANN 9.0 工程。[W01]

### 4.4 READY 和 FREE 必须表示确切的资源状态

READY 不是“已发出 MMAD 指令”，而是消费者所需的 GM 数据已经在依赖顺序上就绪，所以现存代码把通知挂在 `PIPE_FIX`。FREE 不是“算子后处理结束”，而是该 AIV 已经不再读取这个 GM slot，所以挂在 KKT 的 `PIPE_MTE2` 完成位置。[C01]

这让 AIC 可以在 AIV 继续用 UB 中的旧 KKT 做计算时，覆盖已经空闲的 GM slot。释放时点提前的是 **GM slot 的所有权**，不是允许提前覆盖 AIV 的 UB KKT。这两种存储生命周期必须分开。

### 4.5 没有工作也不能随意退出协议

R=1 的短 tail 可能让第二个 AIV 没有行可算。若它直接 return、不消费 READY 或不发出必要 FREE，AIC 可能永远等不到成组释放。现存代码使无工作 lane 仍参与对应轮次的同步；对非法元数据分支也保留计数对称。[C01]

这只是同步健壮性安排，不代表算子承诺对任意非法输入生成有业务意义的正确输出。输入校验与同步不死锁是两个独立要求。

### 4.6 Host 调度是协议的一部分

现存 Host 显式设置 `SetScheduleMode(1U)`，注释说明配对的 MIX slices 需要共同驻留；随后设置 blockDim、tiling key 与 workspace 大小。Kernel 即便 READY/FREE 写对，Host 仍可能通过不匹配的路由或运行配置破坏假设。[C03]

项目后续出现过“Kernel 已改好，Judge 仍 RTE”，最后发现旧 Host 被误用。这证明 Host 不是被动参数容器，而是实际执行协议的一部分。[S03]

## 五、AIV 向量化：BRCB、double-head 与数据预取

### 5.1 逐行标量控制为什么值得移除

epilogue 本质是二维广播：每一行重复使用一个 g_i 或 beta_i，每一列重复使用 g_j。若每行都通过 Scalar 取数、再发起一组 Vector 指令，就会产生较多标量循环、地址计算和同步管理。[S02][H01]

BRCB 的官方语义是把一组标量分别复制到 32 字节数据块。FP32 时，一个标量对应 8 个重复值。随后借助 repeat-stride，让一行中的多个向量 block 重用该标量 block，并在下一行切换到下一个。它不是直接生成整个 `64×64` 广播矩阵。[W02][C01]

### 5.2 一个具体的广播布局

对 64 个 FP32 行标量，BRCB 产生 `64×8=512` 个 FP32 元素，也就是 2 KiB 的行标量 block。两个 head 则预留 1024 个 FP32 元素、4 KiB scratch。通过指令 repeat 参数实现对 64 列的重复使用，避免显式执行 64 次 C++ 行循环。[C01]

```text
g[0] -> [g0 g0 g0 g0 g0 g0 g0 g0]  // 一个 32B block
...
g[63] -> [g63 ... g63]

二维向量指令：
  同一输出行的 8 个 FP32 block 重用一个行标量 block；
  下一次 repeat 切换到下一行标量；
  列向量 g_j 在每一行继续重用。
```

这是布局和指令地址模式的配合，不是改变数学算法。尾部行数、起始偏移和 BRCB 对齐必须单独验证。[C01][S02]

### 5.3 Double-head 具体合并了什么

现存基线每批处理两个连续 query head。gQueue 和 betaQueue 的每个 buffer 各容纳两个 head 的 64 个 token 数据，并保留深度 2。一次带 stride 的描述符可以替代两次分散的小搬运；两个 head 的准备阶段也能一起发射。[C01]

两份 head-specific mask、beta 因子和输出仍然独立。高阶基线采用两个独立的 head-size 输出队列，各自深度 2；不能把“double-head”理解为共享同一份门控结果。共享的是 KKT、执行组织以及部分搬运/调度成本。

### 5.4 把独立数据提前，不把依赖数据误提前

V6.7.1 的标题直接说明两个要点：early g/beta prefetch 与 asynchronous KKT MTE2 overlap。第一批 g/beta 与当前 KKT 无数学依赖，因此可以在等待 READY 前先发起；READY 到达后发起 KKT 搬运，再让 Vector 用已就绪的 g/beta 生成因子。[C01]

只有即将把因子与 KKT 相乘时，才需要等待 KKT 的 `MTE2_V` 事件。在这之前，两条流水可以重叠。待 KKT 读完就先发布 FREE，再发起与它无关的下一批 g/beta 搬运，避免让 AIC 的 slot 重用被后续 MTE2 队列拖延。[C01，396–414 行]

### 5.5 同步削减必须跟着依赖证明

历史记录中出现过逐步减少保守 barrier、先整合两个 head 再调整阶段顺序等实验。局部删除 barrier 并不代表某一类 barrier 全部多余。尤其一个 scratch 先承载广播、后承载 beta 或指数因子时，必须证明前一使用者已结束。[H01][C01][S08]

适合报告的说法是：按生产者、消费者和缓冲区复用边界，逐步缩小等待范围；每次只改一个依赖边，再做完整回归。不能说“删除所有同步，让硬件自动流水”。

### 5.6 未形成主线收益的 AIV 分支

历史项目记忆记录：BF16 KKT workspace 实验被撤回；ratio=1 专用 half-tile key 采用 2048 元素 KKT/输出、4-depth MTE3 窗口并删除 pair UB 后，Judge 基本无变化；high-repeat 门限 16/32 无明显差别，门限 8 略慢。[H02][H04]

前两项保留了明确“撤回/无收益”的结论，但本轮没有恢复完整逐 case 表，不能补写精确退化幅度。特别是 BF16 workspace 的动机虽可解释为减少中间数据量，却不能在没有日志时断定撤回原因一定是精度不通过。

## 六、从高阶 Matmul 转向固定形状 direct-MMAD

### 6.1 为什么还要动 Cube

在已有分组复用和 AIC/AIV 流水之后，单个 Cube 任务仍然只是 M=N=64、K=128 或 256 的小矩阵乘法。高阶 Matmul 的通用迭代器、shape 处理、资源管理和输出调度可能占有不可忽略的控制成本。历史 trace 能看到大量 Matmul 调度与 Scalar 调用路径，这构成了尝试固定形状低阶实现的依据。[S16][S04]

这里不是“高阶 API 总是慢”的结论。它是这个工作负载上一个可检验的假设：固定形状能够消去多少通用控制，是否值得承担手写布局和同步的成本。

### 6.2 手写路径的基本数据流

```text
K 的 GM 存储
    ↓ GM→L1，按所需布局打包
L1 中的 K tile
    ↓ L1→L0A / L0B，按 K-part 组织
MMAD：BF16 × BF16，FP32 累加到 CO1/L0C
    ↓ Fixpipe
固定 64×64 FP32 workspace
    ↓ READY / AIV MTE2
Vector 后处理与输出
```

CO1 是代码中用于矩阵乘法累加/结果的片上张量位置；在这一数据流里对应 L0C 阶段。报告时先解释它的职责，再解释缩写，可以避免把它误认为另一个 GM 临时数组。[S03][S04]

### 6.3 固定 full-pad 64 带来的取舍

新路径把 full 和 tail 的计算/结果布局统一为 64×64。full64 不额外清零；tail 把无效输入行补零，AIV 始终按 64 列 stride 读取。这样可以消除旧 Matmul compact tail 输出带来的分支与转换，但 tail 会执行一些无效乘法。[S04]

本轮推导：若对同一 K 比较理想 `L×L` Gram 与 `64×64` Gram，乘法工作比例为 `(64/L)^2`。L=37 时约 2.99，L=1 时为 4096。这个比值不是最终时间倍率，因为固定开销、Cube 对齐、tail 数量和原实现的转换成本也参与决定结果。

所以 full-pad 的论证应是“在题目 tail 稀少、full64 为主的结构下，以有限冗余计算换固定布局和简单控制”，不是“补零计算免费”。[S01][S04]

### 6.4 K128 与 K256 不能直接视作同一条路径

K-step 固定 64 时，K128 需要两个 K-part，K256 需要四个。K256 会比 K128 更早暴露 L0 stage 重用问题：前两个 part 用完 stage0/1，第三个 part 就可能再次触碰 stage0。[S03]

早期稳定里程碑因此采取受控路由：只有 `K128 && R<=4` 启用手写 packed，其余 K128 与全部 K256 使用 Matmul 基线。这个规则是当时的安全状态，不是项目最后一直没有 K256 手写实现。[S03]

### 6.5 参考了哪些代码，而不是照搬哪些参数

本项目保存了 CATLASS small Matmul、FA QK/PV、FAI QK normal/head-tail、full-load-A ping-pong，以及官方 `mmad.asc` 等源码。可借鉴内容是 stage 资源划分、正反向事件、L1/L0 流水和固定结构，不是把 FlashAttention 的整个调度照搬过来。[C08][C09]

例如 `small_matmul.cpp` 使用 AtlasA2、两级 stage、L1 tile `128×256×256`、L0 tile `128×256×64`，输入/输出为 half，并有 tile 数不超过 AIC 核数、K 不超过 L1 K 的适用条件。这与本题的 BF16 输入、FP32 输出、64×64 Gram 并不相同。[C08]

官方 Matmul 最佳实践与 Matmul+GELU 样例提供了双缓冲、块级同步和 CV 分工的参考，但其中同时出现 A2/A3 与 950、CANN 9.0 与 9.1 等支持范围。项目需要按真实设备和 CANN 分支核对，不能因为接口在一个新架构样例中出现，就假定 910B 当前路径也可直接使用。[S17][S18]

## 七、关键问题深挖：L0 生命周期与多任务死锁

### 7.1 为什么这一问题耗费了很多时间

问题不是单一的“程序不能运行”，而是呈现逐级变化：小 case 可以、某些 K 不可以；单 task 可以、多 task 不可以；本地某轮可以、Judge warmup 挂。只根据 `507015` 这个上层错误码，无法知道究竟是跨核等待、内存冲突，还是某个 task 的流水没有收口。[S03]

原复盘强调，应继续读取设备侧 errorStr、subErrType、PC 以及具体 Cube/MTE/Fixpipe 信息；不能把 `aclrtSynchronizeStreamWithTimeout` 的报错位置当成实际错误发生位置。

### 7.2 第一层：L0B 读写冲突

记录中曾明确出现 `L0B read/write conflict`，subErrType 为 4。其解释是：前一次 MMAD 尚在读取 B，下一次 L1→L0B 已覆盖同一地址。仅把 L0A 做 ping-pong，或仅凭 C++ 顺序看上去“先算再搬”，并不能保证 B 的实际读者已经结束。[S03]

修复方向是让 A/B 的 stage 和反向可写事件分别受到保护。对每一份 L0 地址，都应明确：谁写、谁读、什么时候最后一次读完成，以及哪个事件允许下一次写入。只列出“用了 double buffer”不足以证明安全。

### 7.3 第二层：K256 第三个 K-part 提前重用

K128 的两个 part 可能恰好只各用一次 stage；K256 的第三个 part 则重回 stage0，从而出现 L0A 读写冲突。这说明 K128 正确并没有覆盖“stage 再次使用”的边界。[S03]

当时没有继续强行让所有 K 走手写，而是在 Host 中关闭未验证的 K256 路径。这样的 fail-closed 路由让已验证收益可以独立保留，也让后续定位不再被一个已知失败分支污染。

### 7.4 第三层：单个 task 安全不等于 task 之间安全

更棘手的是 K128 小规模通过，大规模 warmup 仍卡住。复盘中的代表形状是 `T=10016,H=8,Hg=2,K=128,NT=157`，因此有 314 个 `(chunk,kvHead)` 任务。之前只有几十个任务的测试没有充分覆盖每核多轮复用。[S03]

这时需要从“一个 K-part”扩大到“一个 task 的开始与结束”检查事件。跨 task 保留的 flag 状态、stage 复用以及最后一个 part 的 drain，都可能让第一个 task 正确而后续轮次不正确。

### 7.5 决定性的隔离实验：AIC-only

把 AIV 与跨核 READY/FREE 从实验中移开，仅保留 AIC 路径，仍然能复现挂起。这直接削弱了“肯定是 CrossCore 协议错了”的判断，把范围收缩到 AIC 内部的搬运、计算、输出与事件生命周期。[S03]

这一步适合作为报告中的方法论亮点：不是凭经验选择一个怀疑对象，而是通过移除一整层机制，测试故障是否仍然存在。它证明了该复现不需要 AIV 参与，不等于所有 RTE 都与 CrossCore 无关。

### 7.6 最后稳定的修复：L0 事件在 task 内闭合

记录中的稳定 v6 方案把四个 L0 ownership 事件纳入每 task 的初始化与 drain：L0A stage0/1 使用相应事件，L0B stage0/1 使用另外两个事件。首先让所有事件都 task-local 验证，再缩小到需要收口的 L0 事件；L1/CO1 可在已证明安全的边界继续保留流水。[S03]

```text
task begin：预置本 task 可写的 L0 stage
K-part：等待可写 → LoadData → 等待可读 → MMAD → 归还可写
最后一个 K-part 后：完成本 task 对 L0 的最终使用与 drain
task end：没有悬空的 L0 使用者进入下一轮
```

这是一份具体实现的成功修复，不是 Ascend 硬件要求“所有 MMAD kernel 一律每 task 清空所有事件”的普适定律。后续继续优化时，必须从这条已知安全边界重新证明能够跨越的生命周期，而不是把 drain 简单删掉。

### 7.7 第四层：Host 混用造成的假回归

最后一次被认为“修复后仍有 RTE”的提交，记录确认是旧 Host tiling 被混入，重新把未验证的 K256 路径打开了。Kernel 单文件看上去没问题，实际执行路径却已经改变。[S03][H02]

从此应把版本最小单元定义为：Host tiling、Kernel 入口、Kernel header、TilingData、TilingKey，以及编译环境和提交结果。比较两个性能版本，必须比较这个契约集合，而不是只比较一个 `.h`。

### 7.8 排障顺序与验收方式

当时总结的分层法可保留为：空循环→GM/L1 搬运→L1/L0 搬运→MMAD→Fixpipe→CrossCore→AIV。每次只增加一个执行层；多 task、足够的每核轮次、反复 launch 和官方 Judge 分别验收。[S03]

复盘还记录过测试数据自身错误：T 为 786，但 offsets 最后值却是 10016。kernel 的任何调试都应先排除这种输入契约破坏。设备发生第一轮 RTE 后，应停止继续用同一异常上下文做性能比较；带 printf 的运行也可能改变时序，不能用其耗时评价优化。[S03]

**这一问题的核心收获：**异步硬件上的正确性边界是资源生命周期，不是 C++ 函数边界；测试覆盖也应覆盖复用次数，而不仅是输入形状。

## 八、手写路径后续稳定化与编译器友好化

### 8.1 K128 L1 ping-pong 已进入后续代码谱系

七月底的路线文档把跨 task 的 GM→L1 ping-pong 列为后续首选：保持已验证的 L0 task-local 边界，尝试让下一 task 的 K 加载与当前 task 的 MMAD/Fixpipe 重叠。到 8 月 10 日的整包确认和 8 月 12/20 日的入口文件，K128 已使用 `PackedGramMmadCubeStageK128L1PingPong` 类。[S05–S07]

因此它不能再被写成“到现在完全没有实现的未来方向”。不过，本轮没有恢复它独立的一整套 A/B timing，不能给这个单项补一个百分比收益。

### 8.2 K256 后续采用更保守的四物理 stage

8 月 13 日相关 header 明确写了 K256 conservative V2：四份物理 L0A/L0B stage，对应四个 64-wide K-part；不使用每 stage 的 M_MTE1 计数器，也不通过 K_PART 模板展开；四次 MMAD 后进行一次 task-local 的 M→MTE1 drain。[S09]

源码每个 stage 的地址间距为 16 KiB，而单个 `64×64×BF16` 数据块实际为 8 KiB。四个 stage 起点为 0、16、32、48 KiB；不能在报告中把“数据量 8 KiB”和“地址规划间隔 16 KiB”混作同一个容量数字。L0A、L0B 各自按 64 KiB 容量组织。[S09]

这条路径与早期“两份 L0 stage 循环复用”不是同一种策略。它以更明确的物理分区减少 task 内 stage 复用的复杂性，使 K256 不再继承早期第三个 part 覆盖 stage0 的同一风险模式。

### 8.3 同一份 K 的 L1 复用已在代码中出现

同一批后期 K256 源码说明：A/B 都来自同一个 K tile，且它们的 Nd2Nz 打包参数相同，因此逻辑 A1/B1 可以别名到同一块物理 L1。K256 的共享 L1 数据量为 `64×256×2=32 KiB`。[S09]

这与七月底路线文档把 A/B 单次搬运列为“需要谨慎证明布局”的候选形成了前后承接。但不能外推成所有 GEMM 的 A/B 都可共用 L1：这里依赖 Gram 的同源输入及一致的打包方式，L0A 与 L0B 仍承担不同操作数角色。

### 8.4 编译器友好化做过哪些事情

可以从代码和历史记录中确认的方向包括：固定 full64 主路径；把 K128/K256 通过有限模板路由区分；把 tail 特殊逻辑从热路径隔离；避免不必要的运行时 shape/分支；将广播交给 BRCB 与 repeat-stride；降低临时变量和 scratch 的活跃范围；后续 R3/R4 chunk-pair 候选采用编译期 kPair/kHeadCount；让 Host 预计算形状和任务参数。[C01–C07][S09][S11][H02]

这些改写的目标是给编译器更清晰的常量、依赖和生命周期。它们不等于新增算子功能，也不等于每一项都已经测到收益。用户对 full64 double-head 编译器友好主路径的反馈是“无明显收益也无明显退化，可以保留”；另一些后续整理没有用，要求回退。[H02]

### 8.5 少量特化与过度特化的边界

项目中反复要求避免无依据增加 tiling key、任务重排和大范围动态特化。一方面，固定的 K 与 full64 有真实结构依据；另一方面，每多一组 key，就增加 Host/Kernel 路由、ABI、边界和编译产物需要维护的组合。[H02][S03–S05]

后续确实又出现 chunk-pair 模板和相关候选入口，这是实验分支扩展，不与当时“稳定主线不增加 key”的决策矛盾。应当按版本说明适用范围，而不是把不同时点的决策拼成一个从未存在过的最终实现。[S12]

## 九、Beta-on-AIC：数学上可行，工程上暂不划算

### 9.1 实验动机

已有 Gram 后，AIV 还要对每行乘 beta。用户提出把 beta 组织成对角矩阵，计算 `D_beta @ Gram`，把这部分工作转移到 AIC。出发点是利用相对空闲的 Cube，减轻 Vector 的压力。[H04]

这个变换在实数数学中成立：`(D_beta G)[i,j]=beta_i G[i,j]`。但它只迁移 beta 缩放，g 相关比较、指数、mask 和最终输出仍需处理。不能把这一尝试表述为“这样就不需要 AIV 了”。[S01；本轮推导]

### 9.2 为什么不能只看 Cube 算力

本轮成本分析：原来的行缩放需要约 `64²` 次乘法，而直接把对角矩阵当普通稠密矩阵做 `64×64×64` GEMM，会引入许多与零相乘的工作。还必须构造/搬运 D_beta，并让 FP32 Gram 满足新一次 Matmul 的输入布局和精度要求。

此外 beta 随 query head 改变。原先每个 KV head 的 Gram 可以共享 R 次；迁移 beta 以后，每个 head 对应的缩放工作仍需分别完成。空闲的 AIC 是否足以吸收这些额外成本，只有端到端实测才能回答，而不能用峰值 FLOPS 推断。

### 9.3 实际尝试与结果

项目记忆记录：先尝试手写 FP32 MMAD，遇到复杂的 fractal/layout 和同步问题；随后改用高阶 Matmul API，正确性达到 12/15，但普通 case 的时间普遍变为原来的约 6–7 倍，只有极高复用 R=128 基本没有变化。用户决定暂停这一方向。[H04]

本轮没有重新取得这些 15 个测试的完整表格，也没有验证每个失败样本的数值根因。因此，12/15 和 6–7 倍是历史反馈口径，不是这次重跑的数据；更不能据此宣布 FP32 MMAD 在所有相关场景都不可用。

### 9.4 应保留的失败结论

这次实验否定的是“当前实现方式下，单独把行缩放改成对角矩阵 GEMM 可以给本题普遍带来收益”。它没有否定所有数学融合、所有 Cube epilogue 或所有 R=128 特例。

后续要重启，至少需要一个能消除额外布局转换/中间搬运或稠密零计算的新机制，或者证明某个高 R 工作负载里额外 AIC 成本确实可被隐藏。仅把同一条路径写得更复杂，不构成新的优化依据。[H04；本轮分析]

## 十、后期 AIV：指数分解、输出窗口与 Phase C

### 10.1 一个容易混淆的事实：有四类不同的“缓冲”

第一类是 **AIC→AIV 的 GM workspace 双 slot**，解决生产者覆盖消费者未读数据的问题。第二类是 **AIV 输出 tensor 的延迟回收窗口**，MTE3 已经发射，只是晚一点等待和 FreeTensor。第三类是 **delayed-launch 输出 slot**，结果已算好，但主动推迟 MTE3 的发射。第四类是 **pair/chunk-pair 聚合布局**，通过组织多份输出减少搬运或管理操作。[C01][S08–S11]

这些机制操作的是不同时间点和不同资源。把它们都称作 double buffer，会掩盖后期实验真正改变了什么。

### 10.2 输出回收窗口：先发射，后释放

现存高阶基线分别保存 head0/head1 的输出 tensor，累计两个批次后，通过 MTE3→Scalar 事件等待，再释放队列 tensor。后期一些 direct header 出现四批次窗口。此时 MTE3 已经在前面的 CopyOut 中启动。[C01][S19]

这类优化针对的是过早同步和队列管理频率，不会减少必须写出的输出字节数。四窗口代码存在，只能证明做过这一实现，不能独立证明比两窗口更快；历史上也有扩大或改变输出窗口后无收益的记录。[H02][S19]

### 10.3 Delayed launch：结果就绪不等于立刻写回

后期方案让算好的前一份输出保持 pending，等下一份因子准备推进到特定位置后，再调用 `LaunchReadyOutput()`。目的是让输出搬运与合适的 Vector 阶段重叠，同时避免过早挤压下一批输入搬运。[S08][S10]

历史反馈中，某次 delayed 2-slot 本地 trace 从 64.76 μs 降到 58.19/58.50 μs，降低约 9.7%–10.1%；但 Judge 没有明显改善，甚至略有退化。这个结果应完整保留，不能只取本地更快的一半来报告收益。[H03]

### 10.4 Pair-fused 与 double-head 不是同一件事

Double-head 可以只是“两个 head 同批准备、各自输出”；pair-fused 更进一步组织两份输出的队列归属与搬运描述符。相邻 head 在 GM 中相隔的是完整 head 的 T×64 区域，不能把它们自然看成连续相邻的两个 64×64 tile；需要由 stride 或合适的布局表达跨度。[C01][S08][S09]

因此，早期被排除的 pair-contiguous MTE3 实验，与后期作为主线组成部分的 pair-fused 不能视作同一项实验。应按具体布局和时序命名，而不是见到 “pair” 就合并结论。[S06][H05]

### 10.5 指数因子化：减少元素级 Exp 工作

后期源码不再生成完整 diff 矩阵再对 4096 个元素取 Exp，而是利用：

```text
exp(g_i-g_j) = exp(g_i) * exp(-g_j)
rowFactor[i] = beta_i * exp(g_i)
colFactor[j] = exp(-g_j)

factor[i,j] = rowFactor[i] * colFactor[j]
最后按 g_i < g_j 的动态 mask 筛选。
```

对一个完整 head，名义上的 Exp 元素数从 4096 变成 64+64=128，减少 32 倍。这只是指数元素数量，不是 kernel 提速倍数；外积、mask、KKT 乘法和输出仍然要处理完整矩阵。[S08；本轮计数]

源码还直接比较 BRCB 广播出的 g_i 与 g_j，避免先物化全尺寸 FP32 diff 再比较零。mask 生成之后，广播 scratch 的一部分可用于 compact beta，缩短临时数据的活跃区间。[S08]

### 10.6 数学等价不意味着数值范围等价

相关 header 明确将 `c=0` 写成 no-reduce probe：移除 ReduceMin/Max、中心值计算、V↔S 同步与 fallback，并提醒需要 Judge 验证精度与数值范围覆盖。[S08][S10]

本轮数值反例：令 g_i=-1001、g_j=-1000，则真实差值为 -1，`exp(g_i-g_j)` 是正常有限值；分别计算时，FP32 的 `exp(g_i)` 会下溢，而 `exp(-g_j)` 会溢出，乘积可能成为 NaN。二者都是有限输入，因此“差值小于零”并不能自动保证因子化中间值安全。

选择中心 c，写成 `exp(g_i-c)*exp(c-g_j)`，可以改善共同偏移问题，但还需覆盖范围过宽、尾部、相近 g 值以及特殊数值。对不满足安全条件的输入保留直接 diff 路径，是本轮提出的可靠性方向，不是声称历史最终代码已经实现了完整范围保护。

### 10.7 Phase B 与 Phase C 的真实区别

历史主线的关键反馈是：以 delayed 2-slot + pair-fused 为基础，Phase B 在 Muls/Brcb 后较早发射前一份输出；Phase C 先完成一次 PIPE_V barrier，再把 Compare 和两个 column Exp 排入 Vector 流水，然后才 `LaunchReadyOutput()`，随后再等待这个 Vector 阶段。[H05][S08]

```text
Pair 路径的 Phase C：
  Muls(-g) + Brcb(g_i)
  PIPE_V barrier
  Compare(head0/head1) + Exp(column0/column1)
  LaunchReadyOutput(previous pair)
  PIPE_V barrier
  当前 pair 后续 rowFactor / outer product / mask / KKT
```

用户测试认为 Phase C 更快。它支持的判断是：输出发射的时机本身影响端到端性能；“越早 MTE3，overlap 越多，必定越快”不成立。[H05]

内存路径争用、UB/读写端口压力、与 KKT 或下一批 g/beta 的 MTE2 相互影响，是由现象推导出的候选解释。没有补充微基准与计数器之前，不能把其中某一个认定为已经证实的唯一硬件根因。不同存档中的 single/R=1 路径还保留较早的发射点，因此不能概括成“所有分支都改成同一个 Phase C 位置”。[S08][S10；本轮分析]

### 10.8 KKT double-buffer / next-task prefetch 的停止点

8 月 13 日项目结论明确记录：KKT double-buffer 和 next-task KKT prefetch 略有退化，暂时停止；继续以 delayed 2-slot + pair-fused + Phase C 为主线。[H05]

这不等于否定此前成功的 GM workspace 双 slot 或第一批 g/beta 预取。被停止的是另一层 KKT 提前读取与本地缓冲扩展。潜在代价包括额外 UB 资源、输入输出争用和调度开销；这些是解释候选，缺少逐项计数，不能只选一个写成确定结论。

### 10.9 Chunk-pair：沿时间方向聚合

后期候选将相邻两个 chunk 的输出按 `h0c0,h0c1,h1c0,h1c1` 组织：两头两 chunk 最多 64 KiB，一头两 chunk 为 32 KiB。这样可以把同一 head 在 T 维上邻接的两块输出聚合处理。[S09]

对应候选的任务映射不再只是旧的 chunk-major 循环：它通过 KV-major 的 ordinal，使同一 KV head 的相邻 chunk 更容易连续处理。AIC 与 AIV 必须使用一致映射，slot 的未来重用判断也必须依据真正的本地轮次，而不能机械沿用旧 taskId 的公式。[S09]

代码保持了第一块 KKT 读取完成并释放 slot 后，再安排下一块 compact g/beta 的顺序。随后还出现 R4、R234、R3-only 和 compiler-friendly lean 等不同候选。当前证据能说明这些实现存在，不能把每个变体都记为 Judge 收益，也不能确认全部进入最后提交。[S09][S11][S12]

### 10.10 Checkerboard/C+：进一步错开发射的候选

另一个文件把部分 group 维持在 Phase C，另一部分推迟到 Cast 与 row Exp 后再发射 MTE3，试图错开不同核/配对 lane 的写回。它不靠人为增加 barrier 制造延迟，而是换一个已有计算阶段作为发射点。[S10]

这是一个可以解释清楚的候选实现；本轮没有找到其明确用户测试结论，应保留为“已实现、结果待核验”，不能写成“成功消除了内存争用”。

## 十一、大小 case 分化与冠军代码借鉴

### 11.1 能够直接恢复的用户反馈

在 8 月 24 日起、题为“冠军代码借鉴点”的项目对话片段中，用户先后反馈若干改动“没变化”“之前试过，影响不大”，并对部分低风险改动表示保留。另一次改动后，用户明确说“中小 case 变快了，但是大 case 反而慢了点”。随后要求“大 case 回退原调度”。[H06]

后续尝试又出现“太多不该回退的回退到了之前”，用户认为 256 的阈值偏少，希望扩大新调度覆盖范围，因为只有很大的 case 有退化，而中小 case 没有。[H06]

这些反馈足以说明发生了按规模分化的调度权衡，也说明“一刀切回退”没有达到用户要求。但**256 究竟对应任务数、每核轮次还是另一个规模度量，最后改成了多少，哪些文件被替换，本轮没有恢复到足够证据。** 不能擅自把它写成已确认的最终分流条件。

### 11.2 可讲的工程认识与不可讲的结论

可讲的是：一次调度更改对不同规模的收益方向可以不同，应保留中小 case 的收益，同时让真正发生退化的大 case 使用老路径；回退范围要以实际边界验证，而不是凭经验扩大到全部 case。[H06]

不可讲的是：新调度一定是某个具体 swizzle、某种 L2 policy 或某个任务连续性策略；大 case 退化一定由 L2 冲突造成；最终门限已经调到某个新数值。当前只有用户反馈片段，缺少相应 diff 和性能表，无法支持这些细节。

### 11.3 本轮对原因的分析框架

不同规模可能分别受固定开销、任务负载均衡、地址局部性、并发内存请求、每核稳态轮数以及流水填充/排空控制。一个减少小规模调度开销的策略，在长稳态运行时也可能破坏原本较好的请求分散或资源平衡。这是解释方向，不是对那次具体退化的已完成定位。

下一次需要将原调度、新调度、混合调度放在相同环境下，按任务数、R、K、每核轮数、full/tail 分布和逻辑输出字节分桶，逐 case 比较。只有这样才能决定是否需要一个门限，以及门限应使用什么变量。[H06；本轮建议]

## 十二、性能分析方法、资料与能够确认的数据

### 12.1 三层测量要分开

**正确性/运行层：**是否编译、是否完成 launch、是否数值通过、是否存在多轮后才触发的 RTE。这个层面不以性能收益替代结果。[S02][S03]

**本地剖析层：**trace.json、指令流水、每核阶段耗时、调用次数、MTE2/MTE3/Fixpipe 与 Vector/Cube 的重叠。它们帮助解释原因，但采样方法、模拟器模型和真实设备计时必须标清。[S16][W03][W04]

**目标评测层：**Judge 的逐 case 时间、通过情况和总体评分。不同 case 权重、输入规模、缓存状态与运行环境可能改变局部实验的价值。最终提交收益必须以这个层面为准，不能用一张更紧凑的 trace 代替。[H02][H03][H06]

### 12.2 一个实用的关键路径读法

先看 Task Duration 和最后结束的核，而不是只看 AIC/AIV 平均耗时。再检查：AIC 是忙于 MMAD 还是等 FREE；AIV 是等 READY、等 KKT、执行 Vector，还是等输出队列；最后定位较长的等待对应哪个生产者。[C01][S16–S18]

看到 Scalar 中大量 DIV、地址计算、队列/Matmul 管理指令时，可以考虑固定形状、常量提升或减少循环控制；但需要确认它们确实延长了关键路径，而不是隐藏在长时间搬运后面。看到 MTE3 时间较长，也不应直接宣布 HBM 写带宽饱和。

### 12.3 已恢复的定量结果

### 12.4 历史 profiler 数字应该怎样使用

本轮历史检索恢复过一段分析摘录：AIV UB→GM 约 20.46 GB/s、利用率约 10.95%；GM→UB 约 10.71 GB/s、利用率约 4.87%；约 98 条 MTE2 和 33 条 MTE3 指令/AIV；UB→GM 1024 KB/AIV、GM→UB 536 KB/AIV；平均 AIC 40.38 μs、AIV 41.59 μs。[H03]

这些数字没有在本轮从原始 profile 文件重新聚合，单位 KB 也保留原摘录口径，因此只适合放在技术档案的“待原表复核”部分。报告正文若要使用，应先找回对应 shape、版本与工具字段。仅凭两个平均时间接近，不能断言流水完全平衡；仅凭两个带宽值，也不能计算真实系统的剩余可优化百分比。

### 12.5 本轮建立的工作量模型

对所有完整 chunk，Gram 总 FLOPs 近似为 `2×64×T×Hg×K`；输出字节数严格按输出 shape 为 `4×B×H×T×64`。每个完整 head 的 g/beta 有效输入是 `64×(4+2)=384` 字节，而输出为 16 KiB。[S01；本轮推导]

这些关系解释了为什么高 R 情况下只继续缩短 AIC 可能不再有效：Gram 以 Hg 计数，而输出与后处理以 H 计数。反过来，小任务数、低 R 情况可能更容易感受到 Cube 的固定控制成本。模型提供分组方式，不替代测量。

### 12.6 一个可复算的逻辑数据量例子

取历史分析中出现的 `T=1280,H=128,Hg=32,K=128,R=4`，20 个完整 chunk，共 640 个 Gram task。按逻辑路径计算：K 原始数据 10 MiB；若 A/B 从 GM 分别搬入则为 20 MiB；workspace 写 10 MiB；两个 AIV 各读完整 KKT 合计 20 MiB；输出 40 MiB；g/beta 有效数据约 0.9375 MiB。[H01；本轮推导]

因此，按这种搬运结构相加约为 90.94 MiB；如果共享 L1 输入消除重复 K 搬运，则约为 80.94 MiB。**这是接口/路径层面的逻辑数据量，不是物理 HBM 流量。** L2 命中、重复请求、padding、对齐和跨核行为会让真实 DRAM 数字不同。

### 12.7 为什么不能宣布“已经打满带宽/已经极限”

理论下界可用 `max(计算量/有效算力, 数据量/有效带宽)` 作为起点，但本题还有 launch、同步、队列管理、流水填充与排空、双 AIV 不均衡等成本。有效算力/带宽应在匹配的访问方式和并发条件下测量，不能直接用芯片宣传峰值。[本轮分析]

已有实验说明很多朴素增量手段的收益趋弱，但没有建立全 shape 的下界证据。工程上可以说“现有主线进入收益递减阶段”，不能说“已证明达到硬件极限”。

### 12.8 当时参考过什么，本轮又补充了什么

当时保存的参考包括官方 Matmul 基础 API 最佳实践、Matmul+GELU CV 融合示例、`mmad.asc`、CATLASS 小矩阵与 FlashAttention 相关 block-MMAD 文件，以及 CANN 内的 Matmul 实现调用链。[C08][C09][S16–S18]

本轮补充核对的是官方 CrossCore 模式、BRCB 语义、指令级 trace/CSV 字段和 msOpProf 仿真剖析文档。这些用于确认术语与完善后续方法，不冒充项目初期已经阅读并使用过的全部材料。官方文档版本和历史工程版本不同的地方，需要重新核对兼容性。[W01–W05]

### 13.2 语义、布局与功能基线

**E09｜按 query head 独立处理的重复工作。** 主线识别 `(chunk,kvHead)` 共享 Gram，供 R 个 head 使用。结构保留；没有单项完整加速表。[C01][S13]

**E12｜GM workspace READY/FREE 双 slot。** 固定两 slot、交替计数、读完 KKT 即 FREE，Host batch schedule 配合。保留。[C01][C03]

**E14｜double-head 小搬运与因子准备。** g/beta 两头批处理，独立输出队列，共享 KKT。保留于高阶基线。[C01]

**E15｜V3/V3.1/V3.2/V3.3 逐步调整。** 历史检索记录了 tail 退回稳定单缓冲、两头 g/beta 批处理及少量 barrier 削减；缺少每版完整 diff 和结果，不强行排序成逐版提速曲线。[H01]

**E18｜R=1 half-tile 专用 key。** 2048 元素 tile、4-depth MTE3、减少 pair UB；Judge 基本无变化，不再作为主线优先项。[H02]

**E19｜high-repeat 门限 8/16/32。** 16/32 无明显变化，8 略慢。不能据此证明 hidden workload 的 R 范围。[H01]

**E20｜并行双 AIV 的替代调度/下三角计算。** 7 月 27 日对话有反复 RTE；下三角方案被反馈不符合要求、错误且更慢。撤回该尝试，不否定成熟双 AIV 方案。[H02]

**E40｜KKT double-buffer/next-task KKT prefetch。** 略退化，停止。不要与 E12、E16 的成功机制混淆。[H05]

**E41｜chunk-pair R4/R234/R3-only。** 多份源码存在，聚合相邻 chunk 输出并改变任务映射；全部变体的正确性、性能与采纳结果未恢复。[S09]

**E43｜MTE3 checkerboard/C+ 错峰。** 有候选代码；没有足够结果确认收益，保留为待核验历史分支。[S10]

**E44｜冠军代码借鉴后的新调度。** 中小 case 更快、大 case 退化；要求只对真正的大 case 回旧调度。最终阈值与打包状态未恢复。[H06]

**E45｜混合调度的回退范围调整。** 用户认为一版回退过多、256 偏少，要求扩大新路径覆盖。缺少阈值含义与最终值，不写成完成项。[H06]

### 14.3 当前挂载文件的具体身份

`chunk_scaled_dot_kkt_baseline(3).h` 首行写着 V6.7.1，里面是 `ChunkScaledDotKktCubeStage<K_DIM>` 和高阶 `Matmul`；`chunk_scaled_dot_kkt(35).cpp` 也是对应的 Matmul-object 入口。这两份文件属于同一类旧路线，不能仅凭名称认定它们彼此不匹配。[C01][C02]

### 14.4 TilingData 的 ABI 也有代际变化

旧高阶路线携带 TCubeTiling，当前文件要求结构不超过 256 字节，注释关联项目曾出现的 264 字节问题。这个限制是该工程经历和写法，不能推广成所有 CANN tiling 结构的全局上限。[C04]

后期 direct 路线的部分文件只保留 `totalTaskCount,t,hg,blockDim,numRepeat`，并断言结构为 32 字节。即使字段名字相似，旧 Host 与新 Kernel 混用也会破坏解释。后续 chunk-pair 模板又扩展了路由维度，入口、key 与 header 必须同时对应。[S12][S14]

### 14.5 本文能给出的最稳妥结论

能够作为**历史后期优化主线**描述的是：direct-MMAD Gram 路径与稳定 MIX 分工之上，AIV 继续沿 delayed 2-slot + pair-fused + Phase C 推进；KKT UB 双缓冲和 beta-on-AIC 不进入该主线。八月下旬再围绕大小 case 调度权衡进行尝试。[H04–H06][S06–S10]

但是，不能据此自动合成一套代码再称为“你的最终最快版本”。要正式归档最终基线，必须拿到最后 Judge 通过/性能结果对应的七件套，并对版本、ABI 和分支启用条件逐一核对。本次交付的是复盘与报告材料，不是未经验证的最终算子代码包。

## 十五、是否接近极限与下一步实验

### 15.1 当前判断

**没有证据证明已经达到硬件极限；有证据表明原有主线进入收益递减区。** 多项双缓冲、额外 tiling key、beta 迁移与局部微调都没有稳定改善目标评测，而任务调度和发射时机仍显示出 shape-dependent 的空间。[H02–H06]

后续工作的首要目标不应是再“堆一层优化”，而是建立可复现的最后基线与逐 case 瓶颈画像。以下是本轮提出的计划，不冒充已经完成的实验。

### 15.2 P0：把最后基线与测量闭环补齐

固定一套 Host/Kernel/tiling/key，记录 SHA256、CANN/驱动/设备型号、编译选项、启用分支和完整 correctness。每个代表 shape 跑重复测量，保留中位数、分位数与波动；同时记录 task 数、每核 round、R、K、tail 数和输出字节。

验收标准：同一包重复测量的波动可解释；最后一次 Judge 的每个结果能反查到唯一源码集合。没有这一步，再做门限搜索容易比较到不同 ABI 或不同历史基线。

### 15.3 P1：核实与保护指数因子化的数值范围

这是代码已有候选但安全性与最终采纳状态不完整的方向。先加入大共同偏移、极宽 g 范围、相等/近等 g、tail 和非零 beta 的对抗测试；比较直接 diff、居中 factorization、c=0 factorization 三者。

若需要运行时范围判断，必须评估归约和同步成本是否吃掉收益。可以考虑有限 shape/输入契约下静态保证或快速 fallback，但不能靠当前示例数据“看起来 g 不大”替代契约。验收同时包含全精度通过与目标 case 加速。[S08；本轮建议]

### 15.4 P1：建立调度分流的真实边界

围绕新旧调度的差别，按任务数/每核 round、R、K 与输出字节扫描交叉区。先找出稳定的回归区域，再决定门限是否只需要一个变量。门限只能由可公开的 shape/结构推导，不能依赖隐藏测试编号。

这一方向承接用户已经观察到的中小/大 case 分化，而不是宣称已经知道 256 的正确替代值。验收应同时要求中小 case 保住收益、大 case 不退化，并说明最差 case 的变化，而不仅看平均值。[H06；本轮建议]

### 15.5 P1：用最小微基准验证 MTE2/MTE3 发射争用

设计保留相同字节数、地址步长和计算量的测试，只改变输出发射点；再分开测试是否共用 UB 区域、是否配对 AIV 同时写、输入是否命中缓存。把 Phase B/C/C+ 与总时间、MTE2 完成时点、MTE3 完成时点关联起来。

目标是区分“读写路径争用”“队列/Scalar 调度影响”“UB 端口压力”“核间请求同相”等解释。只有原因明确，checkerboard、延迟发射或输出聚合的适用范围才可稳定推广。[H05][S10；本轮建议]

### 15.6 P2：R=3 负载不均衡，但只改该解决的问题

现有分 head 使 R=3 分成 1+2。简化模型中，两侧单 head 成本相同且无其他瓶颈时，负载均衡利用率约 3/4；这是一个理论上限差额，不是 25% 可直接追回的端到端时间。[C01；本轮推导]

可以针对已恢复的 R3 chunk-pair 候选做受控比较，研究跨 chunk 交替 head 所有权或工作粒度；但必须保证 KKT 读取、输出地址、READY/FREE 的参与轮数一致。此前 R3 Hybrid 被排除，因此新实验应明确与旧失败方案的差异，而不是换名重试。[S06][S09]

### 15.7 P2：进一步缩减 Scalar 与队列管理

使用指令热点定位确实处于关键路径的整数除法、重复地址构造、短生命周期对象、重复队列状态更新。按 shape 不变量做有限常量提升，保留 tail 冷路径隔离；对每次变化比较反汇编/IR 与真实性能。

当前已经做过固定 full64、BRCB 和编译期 head 数等改写，所以这不是“从零做编译器友好化”。剩余价值必须由新的指令热点证据支持。[C01][S11][S16；本轮建议]

### 15.8 P3：跨算子布局或融合，需要接口条件变化

若上游能够直接产生紧凑 chunk-major g/beta，可减少本算子搬运描述符和寻址；若下游可以直接消费片上或融合后的结果，则有可能减少中间输出。它们属于图级机会，而不是在当前固定接口里免费获得的优化。[H02；本轮分析]

独立增加一个重排 kernel 会引入 launch 与读写成本，必须计算完整链路。题目要求输出完整 `[B,H,T,64]` 时，也不能通过“不写上三角”“输出稀疏格式”来伪装减少输出量。[S01]

### 15.9 不再列为“完全没实现”的项目

K128 L1 ping-pong、K256 四物理 L0 stage、特定条件下 A/B 共享 L1、BRCB、double-head、early g/beta，以及任务级两 slot，均已有代码或确认记录。真正缺少的是更完整的收益归因、最新代码统一和适用范围验证，而不是这些点从未被尝试。[C01][S06–S09]

## 十六、需要求助的具体问题

### 16.1 同步与事件生命周期的官方说明

最需要的是能够直接对应版本、架构和资源的例子：L0A/L0B 读写完成的准确边界，M_MTE1 等事件在多 task 中复用的约束，计数是否残留/如何收口，以及 MIX mode-2 与 Host schedule 的组合要求。仅给出一段能跑的单 task 示例，难以回答本项目遇到的多轮问题。[S03][C03]

向社区求助时应附最小 AIC-only 复现、具体 K-part/stage 地址表、每轮事件序列和完整设备错误信息，而不是只贴 `507015`。

### 16.2 性能资料需要覆盖并发，不只覆盖单条 API

希望补充 MTE2/MTE3、Vector、Fixpipe 与 UB/L2 路径同时工作时的性能模型，尤其是小 tile、多个短 descriptor、双 AIV 同时输出、不同发射相位的行为。单条 memcpy 峰值不能解释“推迟写回反而更快”的现象。[H05]

最有帮助的形式是公开可运行的 microbenchmark、工具字段解释、对应 trace 以及可复现的参数扫描，而不仅是“建议使用双缓冲”这种通用经验。

### 16.3 编译器可观察性与版本化样例

需要清晰的从 Ascend C 源码到中间表示、汇编和指令 trace 的定位方法，并说明优化选项和 CANN 版本差异。希望官方能提供固定小 GEMM、full/tail 分离、队列别名与 scratch 复用的对比案例，展示何时简化写法真正减少了热点指令。[S16][H02]

这里的请求是性能可解释性，不是要求社区替代本地 profiling。样例如果同时支持多个产品，也应明确哪些分支适用于 Atlas A2/910B，哪些仅适用于更新架构。[S17][S18]

### 16.4 Judge 结果与本地剖析的可比性

需要更清晰地区分 UI 的错误占比、逐样本通过口径、kernel 时间、平均核时间、warmup 和重复次数；对本地 trace 收益未进入 Judge 的情况，最好能有可公开复现的代表性 workload 和环境说明。不能要求泄露 hidden 数据，而是需要足够的评测方法定义。[H03][H07]

### 16.5 项目内部最需要补齐的材料

首先是最后通过版本的七件套、提交时间/编号及完整逐 case 时间。其次是冠军借鉴阶段实际改动的 diff、256 的变量含义与最终分流条件。再次是 no-reduce/factorized Exp 最终采用了何种数值保护，以及每个 chunk-pair 候选是否进入提交。[S06][H06]

这些缺口不妨碍讲清大部分优化过程，但影响“最终最好是多少”“最后代码到底是什么”这两类结论的可审计性。

## 十七、可复用的方法论与报告表述

### 17.1 六条贯穿项目的方法

**先区分参考，再写实现。** 多套文字/示例冲突时，确定主参考并构造能让它们产生不同输出的数据，而不是用更大的单调随机样例重复验证。[S01][S02]

**先画存储，再谈算术。** 逻辑 shape、GM stride、compact/padded、fractal、UB 广播和 mask bit layout 都要明确；不能让“矩阵看起来一样”替代地址证明。[S02–S04][C01]

**先证明所有权，再移动同步。** READY、FREE、可写、可读与回收应该对应具体资源状态。一个消费者没算数据，也可能仍必须参加协议。[C01][S03]

**先分层隔离，再解释错误码。** AIC-only、多轮复用、只开某个 K 路由，都是缩小问题范围的证据；单看 RTE 类别不能直接推出根因。[S03]

**先比较端到端，再赞美局部优化。** 少 Exp、少指令、多 overlap，都只是可能的收益来源。Judge 无收益或大 case 退化应完整记录。[H03–H06]

**先锁定整包，再谈最终版本。** Host、Kernel、tiling、key、环境、提交结果共同构成可复现基线；单文件名或聊天里的“最终”不足够。[S03][S06][C01–C07]

### 17.2 报告中最值得深入的两个问题

第一个建议选择“主参考冲突 + compact tail”：它展示如何从数学契约、对抗测试到物理布局逐层定位正确性，且可用 3×3 数值例子讲清。[S01][S02]

第二个建议选择“direct-MMAD L0 生命周期”：它有明确的症状升级、AIC-only 隔离、每 task 事件收口以及 Host 混用反转，能够展示系统性排障，而不是列 API。[S03]

Phase C 适合作为性能章节的第三个短案例：用来说明为什么优化后期必须重视关键路径和资源争用，而不以“越并行越好”作结。[H05][S08]

### 17.3 可以直接使用的项目总结

“我先把题面主参考、变长边界和物理布局对齐，建立了功能基线；随后利用分组头共享 Gram，把任务组织成 AIC 生产、双 AIV 消费的流水；在 Vector 上使用 BRCB、double-head 和预取减少控制与等待；再针对固定小矩阵尝试 direct-MMAD，并通过分层排障解决 L0 复用与跨 task 生命周期问题。后期优化转向输出发射时机与调度。实验也表明，更多缓冲或把计算迁移到 Cube 不一定更快，最终必须以正确性和目标 case 的端到端测量决定保留。”

这段表述不包含未经补齐的总加速倍数、最终排名或“已经极限”的主张。需要数字时，使用对应实验的原始结果与明确口径，不拼接不同版本的最佳值。
